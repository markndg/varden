## What commit 5924532 actually changed

The diff is only `varden_sdk/sdk.py`. After a locked enforcing contract:

- Action metadata uses the locked mode, not `self.product_mode`.
- A `GuardResult` whose `blocked` property is true raises `VardenBlockedError` even when the HTTP status was not 403.
- Control-plane exceptions use `_live_fail_closed()`. Under a locked enforcing contract, a closed fail mode becomes `VardenBlockedError` instead of returning `None`.

`GuardResult.blocked` stayed:

```python
return (self.decision or {}).get('action') in {'block', 'require_approval'}
```

`VardenClient.guard` still treated only HTTP 403 as a deny, then called `raise_for_status()`, then indexed `data['decision']`. Any other failure fell into `guarded_action`'s `except Exception`. Locked `fail_mode=open` returns `None` from that handler. Interceptors treat `None` as "not blocked" and call the original function.

## Finding 1 — delivered deny executed

**Classification:** confirmed enforcement bypass for specific configurations and response shapes. Not a bypass of the default `guarded` + `fail_mode=closed` path against an unmodified `/sdk/guard` 403.

**Disposition:** fixed on this branch. Not fixed in published 1.0.2. Patch release required.

### Mechanism

`/sdk/guard` in `varden/app_factory.py` raises HTTP 403 when `decision.action` is `block`, `require_approval`, or `approval_required`. If the approval record cannot be persisted, it raises HTTP 503 whose `detail` still contains that deny. The SDK did not read a deny out of a non-403 body.

Two reproduced paths:

1. HTTP 200 with `decision.action` of `approval_required` (also `blocked`). `GuardResult.blocked` is false, so `guarded_action` returns the result. `guard_tool` runs the callable. This happens for both `fail_mode=closed` and `fail_mode=open`. The stock server does not emit this shape; it uses HTTP 403, which the SDK already turns into `VardenBlockedError`.
2. HTTP 503 with `detail.decision.action` of `require_approval`. `raise_for_status()` throws. `fail_mode=closed` on v1.0.2 converts that to `VardenBlockedError` and the tool does not run. `fail_mode=open` returns `None` and the tool runs. The stock server does emit this shape when `approval_store.create_pending` fails. `strict` refuses `fail_mode=open` (`ValueError`). The affected configuration is `guarded` with an explicit `fail_mode=open`.

HTTP 200 with `decision.action == "block"` does **not** execute on v1.0.0, v1.0.1, or v1.0.2. That is the 5924532 path, and it held in the reproduction.

### Reproduction

Isolated detached checkouts of the three tags. The protected callable appends to a list before returning. A stub HTTP client returned the body under test. No released tree was edited.

`v1.0.2` (`aae9041`):

| fail_mode | Response | Outcome | Side effects |
|---|---|---|---|
| closed | 200 `decision.action=approval_required` | executed | 1 |
| closed | 200 `decision.action=block` | blocked | 0 |
| closed | 503 `detail.decision.action=require_approval` | blocked | 0 |
| open | 200 `decision.action=approval_required` | executed | 1 |
| open | 200 `decision.action=block` | blocked | 0 |
| open | 503 `detail.decision.action=require_approval` | executed | 1 |

`v1.0.0` and `v1.0.1` matched those rows, except the closed 503 case raised `HTTPStatusError` with `side_effects=0` (the tool still did not run). v1.0.2 wraps that closed-path exception as `VardenBlockedError`.

The same six inputs on this branch all reported `blocked` with `side_effects=0`.

### Affected versions

Present in the `v1.0.0`, `v1.0.1`, and `v1.0.2` tags. Introduced with the SDK guard client that only special-cased HTTP 403 and only treated `block` and `require_approval` as blocking actions. Commit `5924532` did not close it. Published v1.0.2 does not resolve it.

### Exploitability

- **Default `guarded` / `strict` with `fail_mode=closed`, unmodified control plane:** a policy `block` or `require_approval` is HTTP 403. The reproduction did not execute the tool. This assessment does not call that configuration an exploitable bypass.
- **`guarded` + `fail_mode=open` (explicit, warned):** a runtime fault that makes approval persistence return 503 executes the tool even though the decision was `require_approval`. Trigger is a control-plane fault plus that configuration, not a crafted agent argument by itself. The operation is one policy would hold.
- **Any fail mode, non-stock body:** HTTP 200 with `approval_required` or `blocked` executes the tool. Demonstrated against the SDK. Not demonstrated against the current `/sdk/guard` implementation, which does not return that shape.
- **In-process `object.__setattr__` on the guard** after lock does not open a locked `fail_mode=closed` contract. That part of 5924532 held, and `tests/security/gauntlet/test_sdk_mode_lock.py` still passes.

No CVSS score is assigned here.

### Remediation on this branch

`varden/runtime/guard_response.py` treats `block`, `blocked`, `require_approval`, and `approval_required` as deny actions, including a decision nested under FastAPI `detail`. `VardenClient.guard` and the MCP gateway raise or return blocked **before** fail-open handling when that decision is present. Disconnects, timeouts, and bodies with no deny still follow `fail_mode`.

If `enforcement_contract()` raises, `varden_sdk/sdk.py` and `varden_sdk/patches.py` fail closed instead of reading mutable `product_mode` / `fail_mode`. That second change was not reproduced as a natural fault; it closes a fallback that trusted attacker-influenced local attributes when the registry could not be read.

### Residual risk

- `fail_mode=open` still runs the tool when the control plane is unreachable or returns a non-deny error (including HTTP 503 whose decision is `allow` because audit persistence failed). That is the documented open mode.
- `observe` still records a block and does not prevent the side effect.
- Saved pre-patch references, direct calls to original functions, and arbitrary code in the same interpreter can still skip monkeypatches. Coverage attestation is supposed to drop `ENFORCED` when the live probe fails. That is a documented limitation, not a regression from this change.
- MCP gateway transport errors still surface as a JSON-RPC error and do not write the downstream message (`run_stdio_gateway` catches the exception). A HTTP 200 deny previously returned `blocked: false` and would have been forwarded. The gateway now treats a deny body as blocked.

## Finding 2 — locked contract vs mutable guard state

**Classification:** the published 1.0.2 implementation holds for the cases the gauntlet asserts. Not a new bypass.

After `protect()`, `CoverageRegistry.enforcement_contract()` is what `_live_enforcing`, `_live_fail_closed`, and `_live_product_mode` read when `mode_locked` is set. `VardenGuard.__setattr__` rejects assignment to `product_mode`, `fail_mode`, and `mode`. `object.__setattr__` can still change the instance dict; interceptors do not consult those fields while the contract is locked. `set_session` refuses a different mode, fail mode, require list, or allow-uncovered set. `reset()` while locked raises unless `release_enforcement_lock=True`.

`tests/security/gauntlet/test_sdk_mode_lock.py` covers ContextVar swap, registry reset, allow-uncovered expansion, `object.__setattr__` poison, failed weaker `activate`, concurrent and async `protect`, and observe-mode behaviour. Those tests passed on the baseline and after this branch's fix.

Invariant check against the published tag plus this branch:

| Invariant | Published v1.0.2 | This branch |
|---|---|---|
| A. Local mode cannot downgrade a locked enforcing runtime | Holds for guard attributes and `set_session`. Direct registry field writes (`reg._mode = ...`) are in-process memory writes and remain out of scope, same as calling the original function. | Unchanged, plus fail-closed if the contract cannot be read. |
| B. Locked fail-closed is not opened by local `fail_mode=open` | Holds. Exception path uses the contract. | Holds, including when contract lookup raises. |
| C. A blocked decision prevents execution regardless of HTTP formatting | Holds for HTTP 403 and for HTTP 200 `action=block` or `require_approval`. Does not hold for `approval_required` / `blocked` on HTTP 200, or for a deny nested in a non-403 body when fail mode is open. | Holds for those shapes. Tested with a side-effect counter. |
| D. Disconnect, malformed body, timeout, unexpected exception | Fail-closed locked contract does not run the tool. Fail-open does, by configuration. | Same, except a malformed or non-403 body that still contains a deny no longer counts as a transport failure. |
| E. A failed decision must not become success via exception handling | Violated for finding 1 under `fail_mode=open`. | Closed for deny bodies. |
| F. Metadata uses the locked mode | Holds (`_live_product_mode`). | Holds. |

## Predictive Authority — what v1.0.2 actually guarantees

Source: `varden/predictive_authority/deployment.py`, `registry.py`, `continuity_store.py`, and the gauntlet tests named below. This branch does not change that design.

| Condition | What the code does |
|---|---|
| Session eviction of accumulated authority | Tombstone. Recreate sets `continuity_broken` and enforce applies `failure_mode`. Not a clean slate. `test_gauntlet` eviction tests and `test_pa_durable_continuity.py`. |
| Restart with ContinuityStore bound (control plane DB) | Prior-authority session reintroduction fails safe. `cross_restart_continuity_verified` is always false. Full graph replay is not implemented. |
| Restart without a bound store | Same trace can be treated as new. Documented. Unbound characterization remains in `test_continuity_gate.py`. |
| Missing or corrupt continuity DB, schema mismatch, deleted DB, lock/busy | Process `continuity_degraded` / fail-safe. `test_rc_continuity_faults.py`. |
| Tombstone table exhaustion | Process-wide `TOMBSTONE_HISTORY_INCOMPLETE` until operator registry reset. New keys are not treated as a trusted clean state while degraded. |
| `WEB_CONCURRENCY` / `VARDEN_WORKERS` / `VARDEN_UVICORN_WORKERS` > 1 without allow | `MULTI_WORKER_UNSUPPORTED`. Enforce fails safe. |
| Undeclared `VARDEN_PA_DEPLOYMENT` | `DEPLOYMENT_UNDECLARED`. Enforce fails safe. |
| Two processes, same DB, each declaring `single_worker` | Durable leases can count both and fail safe. `test_gauntlet_AFTER_lease_detects_sibling_single_worker_processes`. |
| Two processes, separate DB paths | Leases do not coordinate. Each process can miss the other's chain. `test_rc_separate_dbs_do_not_claim_cross_worker_coordination` and `test_gauntlet_split_chain_across_declared_single_worker_processes`. |
| `VARDEN_PA_DEPLOYMENT=multi_worker_allowed` or `VARDEN_PA_ALLOW_MULTI_WORKER` | Residual risk accepted. Not shared-state correctness. |
| Worker id | Includes a uuid so PID reuse does not collide (`test_rc_pid_reuse_does_not_collide_worker_ids`). |
| Stale lease | Expired lease is not an active worker (`test_rc_stale_lease_expires`). |
| Graph budget exhaustion | `safe_conclusion` is false when truncated. Not a claim that every path was analysed. |
| Conflicting live graph versions across workers | Not reconciled. There is no cross-process graph merge. |

Detection of more than one worker is a fail-safe signal. It is not evidence that Predictive Authority state is consistent across workers. Enforce mode still requires one worker unless the operator opts into residual risk. Opt-in does not create distributed coordination.

## Public claims

The published GitHub release `v1.0.2` is titled "Varden v1.0.2 — Runtime Security Hardening". Its body is the Vite bump, a link to pull request 69, and the compare link. It does not describe the hardening. That is a documentation gap in the published release, not a code defect. This branch does not edit the live release.

`CHANGELOG.md` for 1.0.2 matches the PA, tenant, demo-isolation, and mode-lock code that is in the tag. It does not mention finding 1. The Unreleased section on this branch does.

`README.md` and `docs/predictive-authority.md` already say filesystem coverage is `PARTIAL`, MCP is `NOT_ROUTED` without the gateway, Predictive Authority is experimental, and multi-worker opt-in is residual risk. Those statements match the code. The README sentence added on this branch describes the deny-body behaviour of this branch and says it is not in the published 1.0.2 package.

No package version bump was made. `pyproject.toml` remains `1.0.2`.
