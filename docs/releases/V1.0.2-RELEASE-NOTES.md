# Varden v1.0.2 release notes

These notes describe the **published** `v1.0.2` tag (annotated tag object `5c02ee7bc36af41bf60d423a3dc5b6647da97764`, commit `aae9041`). The non-403 deny fix is **not** in that tag. It is prepared as 1.0.3 in `docs/releases/V1.0.3-RELEASE-NOTES.md`.

The live GitHub release page, viewed on 2026-10-09, does not contain this text. Its body is the Vite 8.3.1 bump, pull request 69, and the compare link `v1.0.1...v1.0.2`. Updating that page is a maintainer action. This branch does not publish it.

## Overview

v1.0.2 is a security release on top of v1.0.1. The code in the tag stops the protected agent from supplying Predictive Authority configuration, scopes guard and predictive reads to the credential's tenant, isolates the predictive demo from live sessions, and stops a locked runtime from being downgraded by a second `protect()` or by mutating guard mode attributes. Predictive Authority enforce mode fails safe when the process topology is undeclared or when more than one worker is detected, unless the operator explicitly accepts residual risk.

Upgrading from 1.0.0 or 1.0.1 to the published 1.0.2 package is still the right move for those defects. v1.0.2 does not close every enforcement gap found in this review. The further SDK fix is 1.0.3. See [Not in the published tag](#not-in-the-published-tag).

## Security fixes

These are in tag commit `aae9041`.

### Predictive Authority configuration

1.0.0 read `action.metadata.predictive_authority_config` from the agent payload and allowed it to override the operator. `{"mode": "off"}` disabled enforcement for that action. 1.0.2 takes configuration only from the policy file and `VARDEN_PA_*` environment variables, and strips client-supplied `predictive_authority*` metadata at ingest. Regression coverage: `tests/predictive_authority/test_pa_v101_security.py` and `tests/security/gauntlet/test_enforcement_bypass.py`.

### Tenant and demo isolation

`/sdk/guard` and `/sdk/log` use the credential's tenant. Predictive read endpoints ignore a foreign `tenant_id` (the `demo` tenant remains the one extra scope). `POST /predictive/demo` uses an isolated store so a viewer cannot wipe live session state.

### Locked runtime contract

Commit `5924532` is in this tag. After `protect()`:

- The coverage registry contract (`mode`, `fail_mode`, `require_coverage`, `allow_uncovered`, `mode_locked`) is the authority for interceptors.
- A second `protect()` with a different contract raises `RuntimeError` and does not install a weaker guard.
- Assigning `product_mode`, `fail_mode`, or `mode` on the guard raises. Bypassing `__setattr__` does not change the locked contract the interceptors read.
- HTTP 200 with `decision.action` of `block` or `require_approval` raises `VardenBlockedError` when the contract is enforcing.
- If the control plane raises and the locked fail mode is `closed`, the SDK raises `VardenBlockedError` instead of returning `None`.

`tests/security/gauntlet/test_sdk_mode_lock.py` is the regression suite for that lock. It passed on the assessment baseline (791 tests, see Validation).

### Session eviction and tombstones

Evicting a Predictive Authority session that had accumulated authority records a tombstone. Recreating that key marks `continuity_broken` and enforce mode applies `failure_mode`. Dropping a tombstone under the cap sets process-wide `continuity_degraded` (`TOMBSTONE_HISTORY_INCOMPLETE`) until an operator resets the registry. That is fail-safe behaviour. It does not replay the evicted graph.

## Security gauntlet

`docs/security/GAUNTLET-FINDINGS.md` is the finding list from the hardening work that shipped in this tag. Summary of what the tests actually establish:

- Client metadata cannot turn Predictive Authority enforce off.
- Truncated graph analysis does not set `safe_conclusion`.
- Eviction and tombstone exhaustion do not return a fresh allow for a session that had accumulated authority.
- False `ENFORCED` attestation via a poisoned interceptor probe is refused after the probe is sealed.
- Filesystem coverage stays `PARTIAL`. The tests do not claim a race-free sandbox.
- MCP is `ENFORCED` only while the gateway session is the live route. A discovered config without the gateway stays `NOT_ROUTED`.

The gauntlet's mode-lock tests use the control plane's HTTP 403 deny. They do not, by themselves, prove every response shape. That gap is finding G-SDK-RESP-01 below.

## Predictive Authority

Live authority state is process-local. v1.0.2 guarantees:

- Enforce mode requires `VARDEN_PA_DEPLOYMENT=single_worker`, or an explicit `multi_worker_allowed` / `VARDEN_PA_ALLOW_MULTI_WORKER=1`.
- Undeclared topology fails safe (`DEPLOYMENT_UNDECLARED`).
- `WEB_CONCURRENCY`, `VARDEN_WORKERS`, or `VARDEN_UVICORN_WORKERS` greater than 1 fails safe (`MULTI_WORKER_UNSUPPORTED`) unless that opt-in is set.
- Worker leases on one shared control-plane database can see sibling processes that each declared `single_worker`, and then fail safe.
- `cross_restart_continuity_verified` is false. With a bound ContinuityStore, reintroducing a prior-authority session fails safe. The live graph is not reloaded.
- Separate database files do not share leases or authority history.

Detecting more than one worker is not multi-worker correctness. The opt-in flag records that the operator accepts a residual split-brain risk. It does not merge authority graphs.

## Coverage and attestation

Startup attestation and `varden coverage` keep `ENFORCED`, `PARTIAL`, `NOT_ROUTED`, `UNCOVERED`, and related existing states. A surface is not reported `ENFORCED` when its sealed probe fails. Saved references taken before `protect()`, raw sockets, direct `aiohttp` / `urllib3`, and MCP connections that skip the gateway remain outside the enforced set and are reported as such.

## Remaining limitations

In the published tag:

- `guarded` with `fail_mode=open` runs the tool when the control plane errors, including when a 503 body still contains `require_approval`. Reproduced on the tag. See the next section.
- HTTP 200 with `approval_required` or `blocked` runs the tool even when `fail_mode=closed`. The stock server uses HTTP 403 for those actions, so this was not reproduced through an unmodified `/sdk/guard`. It was reproduced against the SDK.
- Predictive Authority does not provide a shared graph across processes or a verified replay across restart.
- Filesystem mediation is `PARTIAL` (symlink and path checks on intercepted APIs, residual TOCTOU).
- `observe` records decisions and does not prevent side effects.
- Arbitrary code in the same interpreter can call a saved original function. Attestation is expected to stop claiming `ENFORCED` for a probe that fails. It cannot stop that call.

## Not in the published tag

Branch `fix/v1.0.2-security-assurance` fixes the response-shape bug. `VardenClient.guard` and the MCP gateway treat `block`, `blocked`, `require_approval`, and `approval_required` as deny decisions on any HTTP status, including a FastAPI `detail` wrapper, before `fail_mode=open` can turn the call into `None`. If the coverage registry cannot be read, interceptors fail closed instead of trusting mutable guard fields.

The same reproduction that executed the tool on tags `v1.0.0`, `v1.0.1`, and `v1.0.2` reports `blocked` and `side_effects=0` with the 1.0.3 parser.

`fail_mode=open` is unchanged for a real transport failure: disconnect, timeout, unexpected exception, or a body that has no decision slot. `observe` is unchanged. `allow`, `warn`, `monitor`, and `sanitise` still execute.

This fix is `## v1.0.3` in `CHANGELOG.md` and `docs/releases/V1.0.3-RELEASE-NOTES.md`. It is not in tag `v1.0.2`.

A draft advisory is in `docs/security/DRAFT-ADVISORY-guard-deny-body.md`. It is not published and has no CVE.

## Compatibility

No public API was removed. `GuardResult.blocked` is now also true for `blocked`, `approval_required`, and a decision nested in the object stored as `decision`. Callers that only checked HTTP 403 still see `VardenBlockedError` for those denies.

`fail_mode=open` no longer proceeds when the body contains a deny. It still proceeds when there is no decision. Deployments that depended on fail-open to run a tool despite an explicit `require_approval` in a 503 body will now block. That dependency was the defect.

Predictive Authority environment variables are unchanged: `VARDEN_PA_DEPLOYMENT`, `VARDEN_PA_ALLOW_MULTI_WORKER`, `VARDEN_PA_MAX_SESSIONS`, `VARDEN_PA_SESSION_IDLE_SECONDS`.

## Upgrade guidance

Install published 1.0.2 if you are on 1.0.0 or 1.0.1 and you run Predictive Authority in enforce mode, or you depend on the tenant, demo, and mode-lock fixes. No migration of policy files is required for those fixes. Set `VARDEN_PA_DEPLOYMENT=single_worker` for PA enforce, or set the explicit multi-worker opt-in with the understanding that it is not shared-state enforcement.

Do not treat the published 1.0.2 package as containing the non-403 deny fix. Until 1.0.3 is installed:

- leave `fail_mode` at its default `closed` for `guarded` and `strict`
- do not put a proxy in front of `/sdk/guard` that turns 403 into another status

`observe` mode is unchanged: it records the decision and does not prevent the side effect.
